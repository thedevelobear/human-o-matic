# 0084. The tools take IDs and paths, answer each request by the argument it names, and reply with compact JSON

- **Status:** Proposed
- **Date:** 2026-11-12

- The tools are the plan's nine, `list_maps`, `open_session`, `get_sections`, `update_sections`, `set_hit_types`, `set_style`, `set_section_controls`, `render` and `export`, and no `preview` ([ADR 0074](0074-a-render-is-heard-from-its-midi-file-in-the-daw-and-there-is-no-live-preview.md)). Each reply is one compact JSON object of counts, bars, facts, controls and statistics, never a note list, with any open requests as `decisions`, as the CLI prints them ([ADR 0015](0015-unclear-input-is-a-decision-request.md)).
- An argument a tool can't use is a tool error whose text says why: a session that doesn't exist or an ID of the wrong form, a map that isn't built in, a `bpm` outside its range ([ADR 0032](0032-bpm-is-the-only-tempo-a-user-gives.md)), a path that isn't absolute once `~` is expanded, a file that isn't MIDI, an answer that names something the song lacks, as `argument.key: why`, an edit that can't be applied, a section that doesn't exist, or an output that exists.
- `open_session(midi_path, from_map, to_map?, instrument?, bpm?, track?)`: `to_map` is `from_map` and `instrument` is `drums` when left out. A `tempo` or `drum_track` request returns `{"decisions": [request]}` and keeps no session, so it is answered by opening again. Otherwise it returns the session ID, the summary `analyze` prints ([ADR 0033](0033-analyze-takes-flags-and-an-answers-file-and-prints-json.md)), `to_kit`, the instrument, the section table and the requests.
- `set_hit_types(session_id, hit_types?, grids?, unmapped?, substitutions?)` takes each answer under the name its request's `answer_with` gives, in the answers file's form. Answers merge by key, null removing one, and are checked against the song before they are kept. It returns the hit types' counts, the answers held and the requests still open.
- `set_style(session_id, style?, seed?, tightness?)` sets the style, the seed and the song's `tightness`, and returns them with the style's defaults.
- `set_section_controls(session_id, controls, section_ids?, note?)` patches the controls of each section given, or the song's, under every section's own, when `section_ids` is left out ([ADR 0080](0080-a-session-holds-what-a-render-needs-and-reads-its-file-again-by-its-hash.md)). A number outside its control's range, here and for `set_style`'s `tightness`, is clamped to it and listed in `clamped` with the value given and the value used. A wrong type or an unknown control is an error, and the stored controls stay as strict as [ADR 0046](0046-controls-are-layered-pydantic-models-with-a-json-round-trip.md) sets them. It returns each section's own controls, every control as it will render, and its `expected` ([ADR 0083](0083-expected-results-are-the-section-rendered-and-measured-by-role.md)).
- `render(session_id, section_ids?, take?)` renders without writing. `take` sets the take of the sections given, or of every section, and is kept. It returns `style`, `seed`, `instrument`, the notes written, kept and dropped, the guards' counts and the conversion report ([ADR 0075](0075-render-s-summary-counts-how-the-notes-were-placed-in-the-target-kit.md)), and for each section given, or all, its bars, group, take, `skip`, its statistics as the CLI prints them, and what they give in words. While a request is open it renders nothing and returns the section table and the requests.
- `export(session_id, output_path, overwrite?)` writes the render to an absolute path ending `.mid` or `.midi` in a folder that exists, and a report beside it, `<name>.report.json`: the summary `render` prints, the session as kept, and each section's statistics. It never writes the input, by its path or as the same file, even with `overwrite`, and refuses an output or a report that exists unless `overwrite` is set. Both files are written aside first and only then take their names, the report first. New files are all or none, so a failure leaves neither behind. With `overwrite` the report, then the MIDI file, each replaces the file of its name, which can't be undone, so a failure between the two would leave the new report beside the old MIDI file. It records the export in the session, and writes nothing while a request is open.

**Why:** Answering each request by the argument it names lets the agent answer any request one way, and the replies are the JSON the CLI prints. A wrong type is a mistake to fix, while a number past its range, "more than full power", is an intent that a clamp keeps and says it kept. A report beside each file says what made it, so takes can be compared later.

**Consequences:** A report is a second file to keep beside each export.
