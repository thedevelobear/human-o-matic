# 0033. `human-o-matic analyze` takes flags and an answers file, and prints a summary and the requests as JSON

- **Status:** Proposed
- **Date:** 2026-11-08

- The console script `human-o-matic` is `human_o_matic.cli:app`, a typer app. `human-o-matic analyze MIDI_FILE --from-map LIBRARY[/KIT] [--track N] [--bpm BPM] [--answers FILE]` normalizes the song's drums ([ADR 0031](0031-the-score-is-frozen-canonical-hits-with-their-source-notes.md)). It only reads: it writes no file and converts to no other kit.
- The answers that are one value are flags. `--from-map` is required and names a built-in kit by the ids of [ADR 0023](0023-built-in-library-ids.md), and a library with one kit needs no kit. `--track` counts from 0, and `--bpm` is a constant tempo from 3.577 to 60,000,000 BPM, a range of tempos a MIDI tempo event can hold ([ADR 0032](0032-bpm-is-the-only-tempo-a-user-gives.md)).
- `--answers` names a JSON object holding any of the other answers a request's `answer_with` names, as `normalize()` takes them:
  - `unmapped`, for `unmapped_notes`: from a pitch of its `details.notes[].pitch`, written in decimal (`"99"`), to an articulation of the kit or `"drop"`.
  - `grids`, for `ambiguous_bars`: from a beat written `"bar,beat"`, its `details.bars[].bar` and `details.bars[].beats[].beat`, both from 0 (`"32,1"` is beat 2 of bar 33), to `"16th"`, `"8th_triplet"`, `"16th_triplet"` or `"32nd"`.
  - `hit_types`, for `hit_types`: from a family of its `details.families[].family` to `{"soft_below": v, "accent_from": v}`, velocities from 1 to 128, either of which may be left out. `{}` makes every note of the family normal.
  - Any other key is an error, and `from_map`, `track` and `bpm` are named as flags.
- It prints one line of compact JSON on stdout, `{"summary": {...}, "decisions": [...]}`, each request as `DecisionRequest.model_dump(mode="json")`, the JSON the MCP layer returns. When the pipeline raises `DecisionRequired` (`tempo` or `drum_track`), there is no score, and the line is `{"decisions": [request]}`.
- The summary is counts, and no note is listed: `file` as given; `kit` as `library/kit`; `track` (`index`, `name`, `reason`); `ppq`, the working resolution, and `source_ppq`; `tempo` (`given`, `replaced`, `bpm` at the start, `changes`, `min_bpm`, `max_bpm`); `time_signatures` (`assumed`, and `changes` as `[bar, "N/D"]` from bar 0); `bars`, up to the bar of the drum track's last note; `notes` (`read` from the drum track, `score`, `pending`, `dropped`); `beats` (`count` of beats with notes, `ambiguous`, and `grids`, the beats on each grid); `families`, the score's notes per family by name; `hit_types` (`soft`, `normal`, `accent`, and `low_confidence`, the notes whose type is a guess); `low_confidence`, the notes read through each low-confidence articulation ([ADR 0025](0025-proposed-names-ship-at-low-confidence.md)). The same file, flags and answers print the same bytes.
- The exit code is 0 when no request is open, and 3 when one is, with the JSON printed either way. A usage error is typer's 2, with a plain message on stderr and never a traceback: a missing or bad flag, a `--bpm` outside its range, a map that isn't built in (naming those that are), a file that isn't MIDI or has no notes, and an answers file that isn't JSON, has the wrong shape, or gives an answer that names something the song lacks or that the kit or the beat can't take (`AnswerError`), told as `argument.key: why` with the key as the file writes it. Any other error is a crash, 1.

**Why:** A request that wants one value is answered by a flag, while unmapped pitches, beats and families are maps from many keys to their answers, which a file holds. Printing what the MCP layer will return means the CLI shows exactly what an agent reads, and a script can tell an open request from an error by the exit code alone. A tempo outside the range could never be written back to a file. Only an error about the answers blames them, so a bug in the pipeline shows as a crash. A beat is written `"bar,beat"` rather than `"bar:beat"`, since `"3:2"` reads as a tuplet in an answer about triplets.

**Consequences:** Each run normalizes from the file again, since the score isn't saved. The `hit_types` request stays open until every family is answered, so a first run nearly always exits 3.
