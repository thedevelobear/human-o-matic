# 0054. `human-o-matic render` writes a new MIDI file by a plan, and prints its summary and each section's statistics as JSON

- **Status:** Accepted. Its `--style` taking only `tight` is amended by [ADR 0070](0070-the-engine-reads-the-styles-from-data-styles.md)
- **Date:** 2026-11-09

- `human-o-matic render MIDI_FILE --from-map LIBRARY[/KIT] --seed N -o OUTPUT [--to-map LIBRARY[/KIT]] [--track N] [--bpm BPM] [--style tight] [--answers FILE] [--plan FILE] [--overwrite]` normalizes the song's drums as `analyze` does ([ADR 0033](0033-analyze-takes-flags-and-an-answers-file-and-prints-json.md)), finds their sections with the file's markers, renders them by a plan ([ADR 0046](0046-controls-are-layered-pydantic-models-with-a-json-round-trip.md)) and writes a new MIDI file.
- `--seed` is required, from 0 to 2^53 - 1. `--to-map` is the kit to write to, and left out it is `--from-map`'s. `--style` takes only `tight`, the one style until calibration, which adds `medium` and `loose` to the command and the code ([ADR 0044](0044-m3-ships-tight-medium-and-loose-styles-pooled-by-tightness.md)). `--track`, `--bpm` and `--from-map` are `analyze`'s.
- `--answers` is `analyze`'s answers file, which also takes `substitutions` for `conversion` requests ([ADR 0048](0048-a-render-writes-the-score-through-the-target-kit-into-the-drum-track.md)).
- `--plan` names a JSON object with the song's `controls` and `sections`, each section's controls by the bar it starts at, counted from 0 as `analyze` prints `start`, such as `{"controls": {"energy": 0.8}, "sections": {"8": {"skip": true}}}`. A start no found section has, an unknown key, or a control out of range or of the wrong type is a usage error. Sections the plan leaves out take the song's controls.
- `-o` is never the input file, even with `--overwrite`, and an existing file is refused unless `--overwrite` is given.
- It prints one line of compact JSON. With the file written: `{"summary": {...}, "sections": [...], "decisions": []}`. The summary has `file`, `output`, `kit`, `to_kit`, `style`, `placeholder` (whether the style is still the placeholders), `seed`, `notes` (`written`, `kept` by sections played as they came in, `dropped` by answers) and `guards`, how many notes each guard moved ([ADR 0050](0050-guards-hold-every-backend-and-keep-each-section-independent.md)). Each section is `start`, `bars`, `group`, `skip` and its `stats`: `notes`, the mean `velocity` of notes not typed soft, `lowest` and `highest`, the `soft` notes' mean, `accent_contrast`, `timing_spread_ms` and `mean_offset_ms` ([ADR 0052](0052-each-control-is-tested-against-the-statistic-it-mainly-drives.md)).
- While any request is open, from normalizing or from placing notes in the target kit, it writes nothing and prints `{"sections": [...], "decisions": [...]}`, the sections as `analyze` prints them, so the plan can name them. A `tempo` or `drum_track` request prints only `{"sections": [], "decisions": [request]}`.
- The exit codes are `analyze`'s: 0 when the file is written, 3 when a request is open, 2 for a usage error with its message on stderr, and 1 for a crash, which writes nothing.

**Why:** It lets the placeholders be heard before calibration and before the MCP layer exists, through the same answers an agent will give. Every hit-type request has to be answered first, as with `analyze`, since a render with guessed types would mislead whoever listens. Leaving `medium` and `loose` out until calibration means no style can be picked that has no numbers of its own.

**Consequences:** A first run nearly always exits 3 until the `hit_types` request is answered. The plan file names sections by the bars the detector found, so a section the user would split differently waits for M4's `update_sections`.
