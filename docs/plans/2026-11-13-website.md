## 1. Goal, scope, non-goals

**Goal:** a public website that musicians reach by a link: they choose a drum MIDI file, answer the page's questions with choices, sliders and checkboxes, and download the re-performed MIDI, to drag into their DAW. They can then leave short feedback. Every file made from their MIDI is gone when they are done ([ADR 0098](../decisions/0098-the-site-is-open-to-anyone-with-its-link-held-by-limits-and-keeps-no-user-s-midi.md)).

**Scope:** a thin layer over the code the MCP server uses, `mcp_server.Tools` and the functions under it, with the skill's question policy and the vocabulary's rows turned into a step-by-step page ([ADR 0097](../decisions/0097-a-website-is-milestone-m7-a-thin-page-over-the-same-engine-that-asks-the-questions-itself.md)). The same session and seed give the same bytes as `human-o-matic render` and the MCP server's `export`.

**Non-goals:**
- Accounts, logins or invite codes ([ADR 0098](../decisions/0098-the-site-is-open-to-anyone-with-its-link-held-by-limits-and-keeps-no-user-s-midi.md)).
- An LLM. The page asks the questions itself, so there is still no API bill or key.
- An audio preview or a piano roll. The user hears the file in their DAW ([ADR 0074](../decisions/0074-a-render-is-heard-from-its-midi-file-in-the-daw-and-there-is-no-live-preview.md)). A piano-roll view is a possible later idea, not part of M7.
- User-supplied maps ([ADR 0010](../decisions/0010-built-in-maps-only.md)), a DAW bridge, piano or guitar.

## 2. What the existing code gives, and what is missing

**Gives:**
- `mcp_server.Tools`: the nine tools as plain methods over a `SessionStore`, taking IDs and paths and returning compact JSON, never a note list ([ADR 0084](../decisions/0084-the-tools-take-ids-and-paths-and-reply-with-compact-json.md)). Decision requests come back as `decisions`, a control past its range is clamped and listed in `clamped`, and `set_section_controls` returns each section's `expected` in words ([ADR 0083](../decisions/0083-expected-results-are-the-section-rendered-and-measured-by-role.md)).
- `session.load_song`, `session.render_session` and `midi.io.midi_bytes`, which `export` writes from. A download can call them and write nothing.
- `get_sections`: each section's `plays`, `pattern`, `guess` and `questions`, which the skill's question policy already shapes.
- `skills/human-o-matic/references/vocabulary.md`, 34 answers and 3 refinements with ranges, and its reader, `read_vocabulary`, in `tools/check_answers.py` ([ADR 0087](../decisions/0087-the-skill-s-answers-are-checked-by-a-table-with-ranges-a-test-of-it-and-an-agent-given-only-the-skill.md)).
- `list_maps`: 17 built-in kits, each with its `map`, name, articulation count and low-confidence count.

**Missing or in the way, found in the code:**
1. `Tools` lives in `mcp_server.py`, which imports the MCP SDK at module level. Measured on the owner's M1 Pro: importing `human_o_matic.mcp_server` takes 0.68 s and brings the process to 80 MB, and `human_o_matic.session` alone 0.26 s and 49 MB. The SDK doesn't exist under Pyodide. `Tools` moves to a module of its own, with an error of its own that `mcp_server.py` turns into the SDK's `ToolError`.
2. `Tools` has no lock: the MCP server's lock is in `mcp_server._compact`. Whatever calls `Tools` for the page must run one call at a time per session.
3. `files.name_new` falls back to an exclusive create only on an `OSError`. Pyodide's `os` has no `link` attribute, so it raises `AttributeError` there (measured). It needs `hasattr(os, "link")`.
4. `session.py` imports `cli.py`, which imports `typer` and `rich`. In a browser that is at least 0.45 MB of wheels for nothing. The models both use (`RenderAnswers`, `BeatKey`, `Pitch`, the summary models) move to a module without `typer`.
5. Some replies and errors hold absolute paths: `open_session`'s `summary.file`, and the errors of `open_session` and `load_song` that name the file. The page's caller replaces them with the display name.
6. No tool lists a kit's articulations, which the `unmapped_notes` form needs. The page's caller adds a read-only `kit_articulations(map)` over the built-in maps.
7. `export` writes the MIDI file and `<name>.report.json`, and records server paths in the session. The download uses `load_song`, `render_session` and `midi_bytes` instead, and a test holds its bytes to `export`'s.
8. `human-o-matic render` has no takes: the site's bytes equal the CLI's at take 0, and `Tools.export`'s for any takes.
9. `resources.data_dir()` finds `data/` beside `src/`, so a wheel doesn't carry it ([ADR 0024](../decisions/0024-built-in-data-is-found-beside-the-source.md)). The site's bundle zips `src/human_o_matic/`, `data/` and `skills/human-o-matic/references/vocabulary.md` at their repository paths, so `resources.data_dir()` and `resources.skill_dir()` find them.
10. `starlette` 1.10.0, `uvicorn` 0.54.0 and `python-multipart` 0.0.33 are in `uv.lock` as dependencies of `mcp`. `httpx` is not. Starlette 1.10's `TestClient` imports `httpx2`, which is in the lock at 2.16.0 through `mcp`, and warns that `httpx` is deprecated for it. FastAPI is not in the lock.

## 3. Measurements

All measured on the owner's machine (Apple M1 Pro, macOS), on songs built in code: the GM kit, 4/4 at 140 BPM, 480 PPQ, a repeating form of intro, verse, chorus, verse, chorus and breakdown with 8th hats or a quarter-note ride, 16th double kick in the choruses, soft snare notes and a tom fill at each section's end, and input timing jittered by a normal spread of 4 ticks: about 17.8 notes a bar. Nothing from `private/` was used. A shared cloud vCPU or a phone is slower by an amount not measured here.

**Native, each tool call through `Tools`, in seconds:**

| Bars (notes, file size) | `open_session` | `set_hit_types` | `get_sections` | `set_section_controls` | `render` | `export` | Peak memory |
|---|---:|---:|---:|---:|---:|---:|---:|
| 76 (1,356, 10 KB) | 0.09 | 0.05 | 0.06 | 0.14 | 0.19 | 0.20 | 89 MB |
| 152 (2,712, 21 KB) | 0.12 | 0.10 | 0.16 | 0.34 | 0.33 | 0.38 | 93 MB |
| 304 (5,424, 41 KB) | 0.27 | 0.22 | 0.30 | 0.68 | 0.73 | 0.75 | 102 MB |
| 608 (10,848, 82 KB) | 0.43 | 0.36 | 0.51 | 1.18 | 1.23 | 1.33 | 119 MB |
| 1,216 (21,696, 164 KB) | 1.02 | 0.71 | 1.33 | 2.70 | 3.01 | 3.23 | 154 MB |

With creative mode on in every section, `render` takes 0.55, 1.08, 3.21 and 8.77 s at 152, 304, 608 and 1,216 bars, and peaks at 96, 106, 131 and 174 MB: it grows faster than the song. Every call reads and normalizes the file again ([ADR 0080](../decisions/0080-a-session-holds-what-a-render-needs-and-reads-its-file-again-by-its-hash.md)), and `set_section_controls` renders the whole song to give `expected`.

**Hostile files, native:** a 0.99 MB file of 330,000 controller events on a second track takes 4.6 s and 386 MB to read, and a 1.98 MB one of 660,000 events 9.4 s and 722 MB: about 1 KB of memory per event. A lone note 8,000 bars after the drums costs 0.24 s, and 5,000 tempo events in 304 bars cost nothing measurable.

**The same renders under Pyodide 314.0.7** (Python 3.14.2, its numpy 2.4.6, pydantic 2.14.3 with pydantic-core 2.50.4's WebAssembly wheel from PyPI, mido 1.3.3), run in Node 26 with the repository's `src/` and `data/` copied in unchanged:

| Bars | Native: read, render (creative render) | Pyodide: read, render (creative render) | Same SHA-256, both renders |
|---|---|---|---|
| 76 | 0.09, 0.10 (0.14) s | 0.16 to 0.31, 0.27 (0.29) s | Yes |
| 304 | 0.33, 0.42 (0.79) s | 0.66, 0.76 (1.37) s | Yes |
| 608 | 0.67, 0.85 (2.13) s | 1.33, 1.70 (3.61) s | Yes |

The two native tables time different things, so the same song's figures differ. The first times each whole tool call, which reads and normalizes the file again before it renders, and whose `render` also measures and describes every section. The table above splits reading the song from rendering it to MIDI bytes, through the functions under the tools. So a 304-bar song's `render` call takes 0.73 s, against 0.42 s for the render alone.

The whole flow through `Tools`, opening a 304-bar song from `gm` to `sleep-token-ii/default`, typing its hits, a split, `medium` at seed 7, two calls of controls, creative mode on one section, a second take of another and an export, writes the same SHA-256 natively (3.1 s) and under Pyodide (7.0 s). Under Pyodide this needed two stand-ins, both of them changes listed in section 2: the MCP SDK's three names, and an `os.link` that raises `OSError`. Pyodide is 1.7 to 2.7 times slower than native here, about 2 for the longer songs. Its WebAssembly heap held 90 MB after the 608-bar renders, and the Node process 481 MB in all. A browser tab's memory was not measured.

NumPy doesn't promise the same random stream across versions or machines ([NumPy's compatibility policy](https://numpy.org/doc/stable/reference/random/compatibility.html)), so the matching bytes are a measured fact for these renders, not a guarantee. CI runs on Linux x86-64, and whether its bytes match macOS arm64 for the same session has not been measured: no test holds a fixed hash today.

**Download sizes of the browser engine,** compressed as a server sends them, measured from the files: the Pyodide runtime 6.33 MB (its WebAssembly 3.53 MB gzipped, its standard library 2.50 MB, and its JavaScript loader and package list 0.29 MB gzipped), numpy 2.96 MB, pydantic-core 1.50 MB, pydantic 0.49 MB, mido 0.05 MB, typing helpers 0.08 MB, and the app's source and data 0.14 MB: about 11.6 MB on a first visit, plus at least 0.45 MB while `typer` and `rich` come with `cli.py`. A browser caches it for later visits.

**Process start-up, native:** a job process forked from a forkserver that has imported the pipeline starts in 6 ms, against 299 ms for a fresh interpreter.

## 4. Three ways to run the engine

| | 1. MCP server and an agent on the site's server | 2. Server-side, no agent and no MCP | 3. In the browser (Pyodide), from static files, with a store for feedback |
|---|---|---|---|
| **Needs** | The MCP server, an LLM per conversation with an API key and bill, a conversation per visitor, the skill, and a chat page | A web process that calls `Tools` in worker processes; uploads, a session secret per visitor, deletion of every file, caps and rate limits on uploads and jobs | A static page whose Web Worker runs `Tools` under Pyodide; a static host and a feedback store, or a small server of our own for both |
| **Server CPU per song session** | Option 2's, plus the agent | Estimated 6 to 25 vCPU-seconds: 4.2 s at 152 bars and 8.5 s at 304 on the M1 Pro, summing measured calls (an open, a hit-type answer, three reads of the sections, six control changes, two takes and two downloads), times an unmeasured 1.5 to 3 for a shared vCPU | None: the visitor's machine renders |
| **Monthly cost, 20 / 200 / 2,000 users** | Option 2's plus the LLM's tokens per conversation, not estimated: ruled out | $0 / $0 / $0 of compute on Cloud Run's free tier, estimated at 2 songs a user and one instance; egress past 1 GB a month, and which regions the tier covers, unverified | $0 / $0 / $0: on Netlify's free plans, where 20 and 200 first visits fit and 2,000 fit a legacy plan's 100 GB but not a credit-based plan's 300 credits; or a 256 MB Fly.io machine listed at $2.35 to $3.34, which Fly waives under $5 a month for a personal organization; estimated (section 10) |
| **What leaves the user's machine** | The MIDI file, and every answer to an LLM provider | The MIDI file, until deleted | Only the feedback form, when sent |
| **Work, estimated** | Most: option 2 plus a chat front end and an LLM's cost control | Seven PRs: the API, the lifecycle and worker processes, then the page | Seven PRs: the bundle and the worker, then the page; no lifecycle, no upload limits on the server |
| **Risks** | API bill, prompt abuse, a key on a public server | CPU abuse, files left behind, cold starts | An 11.6 MB first load, a phone's speed and memory, numpy's version differing from the pinned one, harder tests |
| **The plan's rules** | Breaks "no built-in LLM" | Hold | Hold, with the bytes checked in both runtimes |

**Option 1** would need an LLM on the server, a key and a bill per conversation, and so breaks the plan's "no built-in LLM", and the reason for it, no API bill or key. It is ruled out. The agents in `.claude/agents/`, the orchestrator, developer and qa, are build-time tools that work on this repository: they never run on the site.

**Option 2** is the plain way: a web layer calls the same Python code in the server's process. It works, and costs nothing at these counts on a free tier, but the server then holds every visitor's MIDI and has to delete it, and has to defend its CPU against hostile files and floods. The design it needs is in the appendix.

**Option 3, as a hybrid:** the page is static, a Web Worker loads Pyodide and runs the same `Tools` over a `SessionStore` in the worker's memory, and a static host serves the files, while the feedback form goes to a store (section 10). Measured above, the code runs unchanged apart from the changes in section 2, about twice as slow as native, and with the same bytes.

**Recommendation: option 3, the hybrid** ([ADR 0100](../decisions/0100-the-site-runs-the-engine-in-the-browser-under-pyodide-from-static-files.md), proposed). The MIDI never leaves the user's machine, so "remove every leftover file from the server" holds by construction, no server of ours needs upload caps, job limits or worker processes, and no CPU of ours can be abused through the engine. It can be hosted as static files, for free (section 10). The costs are an 11.6 MB first load, measured in size but not in time, a render about twice as slow as native, an engine at Pyodide's numpy rather than the pinned one, and tests of the Pyodide path that need Node or a browser.

**What would change it:** the owner's browser check in `feat/web-engine` showing a first load or a render too slow on the machines and phones the friends use, a tab running out of memory on a phone, the bytes under Pyodide differing from native for any song in the tests, or the owner declining any tool that can run Pyodide in tests. Each of these leads to option 2. A trained backend from M5 would need its own path in a browser, since PyTorch is not among Pyodide 314.0.7's packages.

## 5. Architecture

The recommended hybrid. Option 2's differences are in the appendix.

```
src/human_o_matic/
  service.py            Tools and its error, moved from mcp_server.py, with no MCP import
  presets.py            the vocabulary table's reader, moved from tools/check_answers.py
  web/
    __init__.py         static_dir(): where the page's files are, found by one function
    worker.py           what the page's Web Worker calls: one entry, JSON in, compact JSON out
    static/             index.html, site.css, js/*.js (ES modules), fonts/, logo, licences; from PR 6, index.html holds the feedback form's static copy
tools/build_site.py     assembles dist/site/: the static files, the pinned Pyodide and wheels, the app's source and data, and _headers
```

Only with the fallback server of our own: `web/app.py`, `web/feedback.py` and a `Dockerfile`, below.

- **Worker API:** `web/worker.py` has one function the worker calls with a JSON request, `{"call": name, "args": {...}}`, from an allowlist: the tools except `export`, plus `download`, `kit_articulations`, `presets` and `reset`. It keeps one `Tools` over a `SessionStore` in the worker's in-memory file system, at `HUMAN_O_MATIC_STATE_DIR=/state` ([ADR 0079](../decisions/0079-sessions-are-json-files-in-the-user-s-state-directory.md)), writes the chosen file to `/song/<random hex>.mid`, and answers in compact JSON with the paths replaced by the display name. `download` returns the MIDI bytes from `load_song`, `render_session` and `midi_bytes`, and writes nothing. The page never sees a note.
- **One call at a time:** the page queues calls to the worker, as the MCP server's lock does.
- **The bundle:** `tools/build_site.py`, a tracked tool checked like `src/` ([ADR 0058](../decisions/0058-tools-are-scripts-checked-like-src.md)), downloads Pyodide and the wheels at exact versions, each checked against a SHA-256 kept in a committed file, zips `src/human_o_matic/`, `data/` and `skills/human-o-matic/references/vocabulary.md` at their repository paths, so `resources.data_dir()` and `resources.skill_dir()` find them, copies `web/static/` as it is, and writes `_headers`, the headers of section 7 for every path, in the form Netlify reads [25 of section 10]. The output, `dist/site/`, is gitignored and never committed. Every file is served from the site's own origin: no CDN.
- **No server of ours on a static host:** on Netlify the site is `dist/site/` with its `_headers`, and feedback is Netlify Forms. Nothing of ours runs on a server, and the site adds no Python dependency.
- **Fallback, a server of our own** (Fly.io or Cloud Run): `web/app.py`, a Starlette app served by uvicorn, run as the console script `human-o-matic-web`. It imports neither numpy nor the engine. It serves `dist/site/` with the security headers, `POST /api/feedback` and `GET /healthz`, and is configured by environment variables only: `HOM_WEB_SITE_DIR`, `HOM_WEB_DATA_DIR` (the feedback store), `HOM_WEB_CLIENT_IP_HEADER`, `HOM_WEB_CLOSED`, and the limits.
- **For that server, Starlette alone, not FastAPI:** Starlette and uvicorn are already locked, and the server has two routes; pydantic models validate the one body. FastAPI would add a package with its own Starlette range for no gain. `starlette==1.10.0` and `uvicorn==0.54.0` become direct dependencies in the PR whose code first imports them ([ADR 0004](../decisions/0004-exact-dependency-versions.md), [ADR 0012](../decisions/0012-runtime-dependencies-arrive-with-their-milestone.md)), and `httpx2==2.16.0` a dev dependency for Starlette's `TestClient`, already locked. `python-multipart` stays out: nothing is uploaded.
- **Frontend: a page with no build step.** One HTML file, one stylesheet and a few small ES modules, with native form controls. Compared:

  | | (a) Static page, ES modules, native controls | (b) Server templates and a little JS | (c) A framework with a Node build |
  |---|---|---|---|
  | Fit | The page is a step flow over a worker; the static host needs nothing else | Needs a server to render, which the hybrid doesn't have | Fits large apps, not seven steps |
  | Tools | None | A template engine, a dependency | Node, npm and a bundler |
  | Recommended | Yes | No | No |

  JavaScript has no checks in the Python toolchain. The options are in the open questions: none beyond the Python tests of what the page calls and a parse of the HTML, or Node in CI, which the Pyodide test needs anyway, running `node --test` on the page's pure modules with no npm package.
- **The repository's rules hold:** pyright strict on `src/` and `tools/`, the same session and seed give the same bytes in the CLI, the MCP server and the page, no library is special-cased ([ADR 0008](../decisions/0008-library-neutral-drum-maps.md)), maps are built in ([ADR 0010](../decisions/0010-built-in-maps-only.md)), and nothing from `private/` is shipped ([ADR 0007](../decisions/0007-local-only-files-live-in-private.md)).

## 6. The page

**Steps:** 1 Choose a file, 2 Kits, 3 Check, 4 Drummer, 5 Sections, 6 Review, 7 Download, 8 Feedback. The engine starts loading in the worker when the page opens, with a progress bar, while the user chooses a file.

```
+----------------------------------------------------------------------+
| [logo] human-o-matic      1 File  2 Kits  3 Check  4 Drummer          |
|                            5 Sections  6 Review  7 Download            |
+----------------------------------------------------------------------+
| Sections   [A 1-8][B 9-24       ][C 25-40      ][B 41-56      ][D 57-64]|
|            ( split ) ( merge ) ( move ) ( rename ) ( another take )   |
|                                                                        |
| B, bars 9 to 24: crash riding, half-time      pattern  X.x.x.x.X.x.x.  |
| What's the energy here?                                                |
|  (o) chorus, big and open   ( ) halftime, heavy   ( ) your call        |
|  Energy       [==========o----]  0.80  big                             |
|  Groove       [======o--------]  0.50                                  |
|  > Fine-tune: dynamic range, tightness, feel, arc, fills, soft notes   |
|  [ ] Leave this section as it is    [ ] Add notes (off)                |
|  "Big and open: kick about 110 to 121, backbeats 114 to 124 ..."       |
|                                         ( Back )  ( Next group > )     |
+----------------------------------------------------------------------+
```

- **Choose a file:** a file picker and a drop zone, `.mid` or `.midi`, read in the browser. The worker checks the size and the `MThd` header before parsing, and the other caps (section 7) after parsing and before normalizing, and says plainly what is wrong. The file's name is kept only as a label and for the download's name.
- **Kits:** "Where did this MIDI come from?" lists the libraries by name from `list_maps`, with "General MIDI, or I don't know" first, `gm`, as the default. "Which drum instrument will play it?" defaults to the same kit. Kits whose names are mostly inferred say "mapping not yet checked". An `unmapped_notes` request offers to go back and choose another kit. Changing a kit opens a new session.
- **Check, one batch (policy rule 1):** the sections as a strip, the hit types, the unclear beats, and every open request, each with its own form, from the request's `message`, `options` and `details`:

  | Request | Form | Answered with |
  |---|---|---|
  | `tempo` | a BPM number field | `open_session(bpm=)` again |
  | `drum_track` | the tracks from `options`, one to choose | `open_session(track=)` again |
  | `hit_types` | per family, its counts and velocity ranges, "soft below" and "accent from" set between the groups, and "all normal" | `set_hit_types(hit_types=)` |
  | `ambiguous_bars` | per beat, its guess and alternatives | `set_hit_types(grids=)` |
  | `unmapped_notes` | per pitch, an articulation of the source kit from `kit_articulations`, or "leave out", or another kit | `set_hit_types(unmapped=)` |
  | `conversion` | the request's `options` | `set_hit_types(substitutions=)` |

  An unknown kind shows its `message` and options, and a test fails until it has a form of its own.
- **Drummer, the song-wide round (rule 2):** the four style answers of the vocabulary, "tight, modern metal", "somewhere in between", "loose, like a live drummer" and "machine tight, nearly quantized", then a song-wide feel if the user wants one, through `set_style` and `set_section_controls` without `section_ids`.
- **Sections, per repeat group in song order (rules 3 to 5):** each group's `plays`, `pattern` and `questions` from `get_sections`, answered by presets: section kinds for energy, "soft notes more present" or "tucked away", "steady and even" or "more groove", the fill rows, and "your call", which sets nothing. Repeats inherit their group's controls, and the last repeat asks "the same, or bigger?". Under "Fine-tune", the controls as sliders, starting at the resolved values: `energy`, `groove`, `dynamic_range`, `tightness`, `fill_intensity` and `ghost_level` from 0 to 1, `feel` from pushed to laid back, `arc` as steady, build or drop, and checkboxes for `skip` ("leave this section as it is") and `creative`.
- **Added notes:** the `creative` checkbox is off by default and never raised by a question ([ADR 0096](../decisions/0096-the-skill-turns-creative-mode-on-only-when-the-user-asks-for-added-notes.md)). It reads: "Add notes: lets this section add ghost notes, cymbals where it has few, a fill into the next section, flams, rimshots and chokes, only on drums it already plays. Your own notes stay."
- **Echo (rule 6):** after each change the page shows `expected` from `set_section_controls`, any `clamped`, and the questions asked so far against the budget of about 12 ([ADR 0090](../decisions/0090-the-skill-counts-its-questions-the-confirmation-batch-as-one.md)).
- **Section edits:** split, merge, move a boundary and rename, through `update_sections`, all or none ([ADR 0081](../decisions/0081-sections-are-edited-by-split-merge-move-and-rename-all-or-none.md)). Bars show from 1, as a DAW does. "Another take" renders a section again with `render(section_ids, take)`, and "a new take of the song" sets a new seed with `set_style`. The seed is shown.
- **Download:** `<name>-humanized-<n>.mid`, from the original name with anything but letters, digits, spaces, `-`, `_` and parentheses removed and cut to 80 characters, `n` counting this visit's downloads from 1, so the original is recognisable and never overwritten. The report JSON is not offered: it holds paths and the whole session. The page says how to listen: drag the file onto the track whose drum instrument is the kit chosen to play it, and play from the bars it names, with what the summary's `conversion` says to listen for ([ADR 0074](../decisions/0074-a-render-is-heard-from-its-midi-file-in-the-daw-and-there-is-no-live-preview.md)).
- **Review:** every section's `says` from `render`, what the summary's `conversion` reports, any added notes, and the questions asked against the budget, before the download.
- **Feedback:** after a download, an optional form, with the settings it will send shown beside it ([ADR 0099](../decisions/0099-the-site-s-feedback-form-keeps-text-and-settings-never-midi.md)). Its fields are the same in the page and in the static copy that Netlify's form detection reads:
  - `form-name`, `feedback`, which Netlify needs, and `bot-field`, the honeypot, left empty;
  - `rating`, from 1 to 5; `comment`, up to 2,000 characters; and `contact`, up to 200, optional;
  - `settings`, one field of JSON text with exactly these keys: `from_map`, `to_map`, `style`, `seed`, `bars`, `sections` (how many), `song_controls` (the song's own controls), `section_controls` (each section's own controls, in song order), and `takes` (each section's take, in song order) only if question 7 of section 14 says so. Controls are named as `ControlVector`'s fields.
  Netlify needs every field in the static HTML, so the settings travel as one JSON field, not a field a control.
- **Start over and delete:** "Delete my file now" ends the worker, which frees its memory and everything in it.

**The question flow depends on M4's gate.** If variant 4 beats 3, the flow above stands. If it doesn't, questions aren't paying for themselves: the page keeps the song-wide round, and the per-group questions become an optional "fine-tune" step. If variant 5 matches 4, timing defaults change in the engine, not the page. `feat/web-questions` is built after the gate for this reason.

**One source for the presets:** the reader of `vocabulary.md` moves from `tools/check_answers.py` into `src/human_o_matic/presets.py`, which the tool then imports, and `resources` gains `skill_dir()` beside `data_dir()`. The worker's `presets` call reads the bundled `vocabulary.md` and returns each row's controls at their starting points. The page names rows by their answer text only, and a test holds every name it uses to a row of the table. No number of the vocabulary is written in the page.

## 7. Security and abuse

**Limits, in the browser** (they protect the user's tab, not a server; numbers to confirm): at most 512 KB a file, 64 tracks, 100,000 events, 600 bars and 10,000 tempo events, checked in the worker after parsing and before normalizing. The longest drum-only song measured, 1,216 bars, is 164 KB, and a 1 MB file of controller events takes 386 MB natively to read. 600 bars is 20 minutes at 120 BPM, and its creative render took 3.6 s under Pyodide on the M1 Pro.

**On Netlify,** the recommendation, there is no server of ours: the host serves the static files and its form service takes the feedback.
- **What the host enforces:** Netlify Forms takes URL-encoded posts to the site's own origin, up to 8 MB a request, checks them with Akismet and a honeypot field, and states no rate limit [28 of section 10]. The page caps a comment at 2,000 characters and a contact at 200 with `maxlength`, but no code of ours can refuse a longer post or rate-limit a client there. The free plan's hard limit stops a bandwidth flood with a pause instead of a bill [22, 23 of section 10].
- **Kill switch:** deploy a "closed for now" build of `dist/site/`, or delete the form, after which posts get a 404 [28 of section 10]. An invite code, if ever needed, would need a check in front of the engine's files: password protection, which Netlify's credit-based Free plan lacks [22 of section 10], or a server of our own. Either way the engine doesn't change.
- **CSRF:** the site sets no cookie, so there is nothing to forge. A forged feedback post is spam, for Akismet and the honeypot.
- **Logs** are Netlify's, not ours: what they hold and for how long was not checked, so the notice says the host may keep request logs, under its own policy.

**With a server of our own** (Fly.io or Cloud Run, the fallback):
- Request bodies are capped at 16 KB, by the app, which counts the bytes it reads and refuses past the cap or a larger `Content-Length`, and by the proxy, where the host allows it. Only `POST /api/feedback` takes a body.
- A per-client rate limit on feedback, 5 an hour, and a site-wide 200 a day, held in memory. The client is the address the host's proxy gives in the header `HOM_WEB_CLIENT_IP_HEADER` names, such as `Fly-Client-IP`, trusted only behind that proxy, and otherwise the socket's peer. Addresses are kept in memory for the limit's window only, never written.
- Static files need no rate limit at the app; a bandwidth flood costs what the host charges for egress (section 10).
- **Kill switch:** `HOM_WEB_CLOSED=1` serves a short "closed for now" page and refuses feedback. An invite code, if ever needed, is a code exchanged for a cookie in front of the engine's files, with no change to the engine.
- **CSRF:** no cookie; `POST /api/feedback` still checks that `Origin` is the site's own and that the body is `application/json`.
- **Logs** hold the method, the route's template, the status and the time taken: no file name, no note, no feedback text and no client address. uvicorn's access log is off. They are kept as long as the host keeps logs, set as short as it allows, and that period is stated in the privacy notice.

**Either way:**
- **Headers on every response,** from `_headers` on a static host or from the app: `Content-Security-Policy: default-src 'none'; script-src 'self' 'wasm-unsafe-eval'; worker-src 'self'; connect-src 'self'; style-src 'self'; img-src 'self'; font-src 'self'; form-action 'self'; base-uri 'none'; frame-ancestors 'none'` (WebAssembly needs `'wasm-unsafe-eval'`; whether Pyodide needs more under this policy is checked in `feat/web-engine`), `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `Cross-Origin-Opener-Policy: same-origin`, `Cross-Origin-Resource-Policy: same-origin`, `Permissions-Policy` turning off camera, microphone and location, `Strict-Transport-Security` behind HTTPS, `Content-Type: application/wasm` for `.wasm`, and `Cache-Control: public, max-age=31536000, immutable` for Pyodide's and the wheels' versioned paths. A server's API replies are `Cache-Control: no-store`. No inline script or style, and no third-party request: fonts and Pyodide are self-hosted.
- **Errors** say what is wrong in plain words and never hold a path, a stack or a version.
- **Paths:** nothing the user gives reaches a server's file system. In the worker, the file's bytes go to a name the worker draws.
- **Dependencies:** exact versions in `pyproject.toml` and `uv.lock` ([ADR 0004](../decisions/0004-exact-dependency-versions.md)); Pyodide and its wheels by exact version and SHA-256 in the bundle's committed list.

## 8. Privacy and legal

**This is not legal advice.** If any of the audience is in the EU or the UK, the GDPR applies to anything that identifies a person, such as a comment or a contact address. The owner should check the notice and the retention below, and whether anything else applies.

- **What is kept:** under the hybrid, the user's MIDI never leaves their machine: it is read in the browser, rendered in its worker and downloaded from its memory, and the worker is ended by "delete my file now", "start over" or closing the tab. Nothing is written to the browser's storage. The host keeps the feedback a user chooses to send, until the owner deletes it, and its own request logs. On Netlify, the recommendation, that is Netlify Forms: Netlify, a third party, stores each submission in its own database, records the sender's IP address with it, by its staff's answers of 2020 to 2022, and checks it for spam with Akismet; it states no region or retention, and the owner exports and deletes submissions in its UI or API [28, 29 of section 10]. With a server of our own, it is SQLite on the host's volume ([ADR 0098](../decisions/0098-the-site-is-open-to-anyone-with-its-link-held-by-limits-and-keeps-no-user-s-midi.md), [ADR 0099](../decisions/0099-the-site-s-feedback-form-keeps-text-and-settings-never-midi.md)).
- **Nothing left behind:** after an interrupted download, a closed tab, a page reload or a server restart, nothing of the user's is on the server, because the file never reaches it. In the browser, the file, its session and its renders live only in the Web Worker's memory, Pyodide's in-memory file system, which is freed when "delete my file now" or "start over" ends the worker, or when the tab is closed or reloaded. A download is a Blob URL in the page's memory, revoked shortly after the download starts, and an interrupted one is started again from the open page. The page writes nothing to `localStorage`, IndexedDB or Cache Storage, which a scan checks for the page's own code and the first PR's browser check for Pyodide's, and the browser's HTTP cache holds only the site's own files, the page and the engine, never the user's, so a reload starts afresh and there is nothing to clear. If a later change ever stores anything in the browser, the notice says what, and the page gets a button that clears it. The downloaded file, in the user's own folder, is theirs.
- **Feedback** holds the rating, the comment, the optional contact, and the settings the render used: the kits, style, seed, the song's bars, the number of sections and each section's controls. The page never sends the file, its name, its hash, a note, a section's words or a session ID, and no code of ours stores the client's address; Netlify Forms records it itself, and the notice says so. The form service accepts whatever a client posts, so this is the page's guarantee, and the host's limit of about 8 MB a request, which Netlify states for forms with uploads, is the only cap on what a client could post ([ADR 0099](../decisions/0099-the-site-s-feedback-form-keeps-text-and-settings-never-midi.md)).
- **The notice,** short and plain, on the first step: "Your MIDI file stays on your computer: it is processed in your browser and never uploaded. If you send feedback, we keep what you write and the kits and settings you used, until we delete it; the page never sends your file, its name or its notes. Your feedback is stored by our host, Netlify, which also records your IP address with it and checks it for spam with Akismet. Our host may keep request logs, under its own policy. Only use files you have the right to use." It names who runs the site and how to ask for feedback to be deleted, both for the owner to fill in. The owner checks the sentence about Netlify against its current terms before launch, since what Forms records was read from its staff's answers, not its docs. With a server of our own, that sentence becomes one about the host's logs.
- **Cookies:** none. With no cookie and no browser storage, no consent banner is needed for them (to be confirmed by the owner, as above).
- **`private/`** still holds: nothing from it is shipped ([ADR 0007](../decisions/0007-local-only-files-live-in-private.md)). If the site offers a demo song, it is built in code at build time, as the tests build theirs.

## 12. Tests

A test builds the MIDI it needs in code, in `tmp_path`, with `tests/midi_files.py` and `tests/grooves.py`.
- **Round trip:** a song built in code through the worker API, file to download, gives the same bytes as `Tools.export` for any takes and as `human-o-matic render` at take 0, for the same plan and seed.
- **Fixed hash:** a committed SHA-256 of one such render, so CI on Linux and the owner's Mac show whether the platforms agree, and the Pyodide check whether the runtimes do.
- **Nothing kept:** the page's only request with a body is the feedback form; the worker's `reset` leaves its in-memory file system empty; and the page's own JavaScript uses no `localStorage`, `sessionStorage`, `indexedDB` or `caches`.
- **What the scans cover:** the page's own files, `index.html`, `site.css`, `js/`, the fonts, the logo and `_headers`. Not Pyodide's runtime, Emscripten's loader or the wheels, which may hold URLs and storage calls of their own, so the tests can't fail on them. At run time the CSP blocks a request to another origin, and the first PR's browser check confirms in the browser's network and storage panels that the page makes none and that Pyodide stores nothing.
- **Hostile files:** past each cap, a file that isn't MIDI, or one with no `MThd`, is refused in plain words, and the worker's file system holds nothing after.
- **Limits:** the closed build; with the fallback server, the body cap, the feedback rate limits and the closed switch.
- **No note list:** no reply of the worker API holds a list of notes, as the MCP tests check ([ADR 0084](../decisions/0084-the-tools-take-ids-and-paths-and-reply-with-compact-json.md)).
- **No path:** no reply or error of the worker API holds the worker's paths.
- **Headers and CSP:** for every path of the built `_headers`, and, with the fallback server, on every response.
- **Presets** equal `vocabulary.md`.
- **Accessibility, automated in Python:** every input has a label, the page has `lang`, every image alt text, no inline script or style. A real browser's checks, such as axe, need a headless browser, an owner decision; otherwise they are a checklist at the gate.

## 13. Risks

1. **M4's gate may find variant 4 doesn't beat 3.** Then the page asks a few song-wide questions and keeps per-group fine-tuning optional; only `feat/web-questions` changes.
2. **Friends won't know their kit's `from_map`.** "General MIDI, or I don't know" is the default, an `unmapped_notes` request offers another kit, and the to-kit defaults to the same. A later idea: show how many of the file's notes each built-in kit reads, from the maps' data alone, so no library is special.
3. **Slow first load or render** on old machines or phones. The browser check in `feat/web-engine` measures it before the rest is built, and option 2 is the fallback.
4. **Bytes differing between runtimes** after a numpy or Pyodide upgrade. The fixed-hash test catches it; upgrade them deliberately, together.
5. **Abuse:** with the hybrid, only the feedback form and bandwidth can be abused. On Netlify, Akismet, the honeypot and the free plan's hard stop cover them, and no rate limit of ours applies; with a server of our own, its rate limits, body cap and closed switch do.
6. **The Jetsons are someone else's property.** Style only, original artwork, open-licensed fonts, and the logo checked by the owner.
7. **GDPR** applies to comments and contacts that identify people. Keep feedback minimal and deletable, and the owner checks the notice.
8. **Free tiers change, and free machines sleep.** The build is host-neutral, so moving host is a deploy, not a rewrite.
9. **Netlify's pause is team-wide on a credit-based plan.** A surge on the new site pauses the owner's two existing sites until the next cycle; on a legacy plan, whether the limits are the team's or each site's is unverified. A team of its own, if it has credits of its own, or Fly.io avoids that.

## Appendix: if the engine runs on the server (option 2)

What changes if the owner chooses option 2. Numbers are proposals to confirm.

- **The web layer** calls `Tools` (moved out of `mcp_server.py`, as in PR 1) in **job processes** forked from a forkserver that has imported the pipeline, measured at 6 ms to start, each killed past a 30-second timeout and limited in memory by the container. A global semaphore runs at most as many jobs as the machine has vCPUs, and a short queue answers "busy, try again in a minute" past it. A per-session lock in the single web process runs one job per session at a time, so two tabs can't lose each other's writes.
- **The session secret:** a random 256-bit token in a `__Host-` cookie, `HttpOnly`, `Secure` and `SameSite=Strict`. The workspace directory is named by the token's SHA-256, so neither the token nor another visitor's directory can be read off the disk, and the browser never sends a session ID: the server finds the one session in the workspace. The 12-digit session ID stays as it is ([ADR 0080](../decisions/0080-a-session-holds-what-a-render-needs-and-reads-its-file-again-by-its-hash.md)). State-changing requests also check `Origin`.
- **Where files live:** one site directory, `HUMAN_O_MATIC_STATE_DIR`, ideally on a RAM disk, holding a workspace per visitor: the upload as `in-<hex>.mid`, `sessions/<id>.json`, any `.<id>.*.tmp` left by a killed write, and `workspace.json` with its deadlines. The download is streamed from memory, so no export or `.report.json` is ever written.
- **Uploads:** the raw file as the request body, not a multipart form, so nothing is spooled to the system's temporary directory. Caps: 512 KB, checked by `Content-Length` and by counting bytes; `.mid` or `.midi`; `MThd`; then the browser caps above, checked in the job before normalizing. The original name is a sanitised label only.
- **Deletion,** by deadlines written when the files are made, so no deletion depends on the browser: the workspace goes 15 minutes after its last download, at once on "delete my files now", after 30 idle minutes, and 2 hours after upload at the latest. A sweep every 5 minutes enforces them, and every start deletes every workspace. An interrupted download, a closed tab and a restart are all covered by the deadlines and the start-up sweep. A second take after a download is allowed until a deadline passes.
- **Rate limits:** 10 uploads an hour and 120 calls a minute per client, by the trusted forwarded address.
- **Hosting:** Cloud Run's free tier with at most one instance, so a session stays on the instance that holds it, or a Fly.io machine with 512 MB. Peak memory measured natively: about 130 MB for a 600-bar creative render in one process.
- **PRs:** `feat/web-api` and `feat/web-lifecycle` replace `feat/web-engine` and `feat/web-site`, the server of our own of section 5 serves the page, and the privacy notice says the file is uploaded and when it is deleted.
